# طرح مهاجرت افزایشی و امن تأمین ملزومات

وضعیت: **طرح مستند؛ اجرا نشده است**  
دامنه: شیت‌های نیاز مواد، سفارش‌ها، ردیف سفارش، تخصیص‌ها، دریافت‌ها، تنظیمات اتصال رویداد، مشخصات مصرف و تاریخچه محاسبات.  
محدودیت: این سند مجوز تغییر داده یا schema در محیط تست/زنده نیست. تا زمان بررسی read-only شیت واقعی، هیچ migrationی اجرا نشود.

## 1. نتیجه فعلی

بر اساس تعریف‌های DatabaseSetup.js و قراردادهای موجود، هنوز تغییر schema ضروری و تأییدشده‌ای شناسایی نشده است. تعریف header در سورس اثبات نمی‌کند که شیت واقعی همین headerها را دارد. بنابراین اولین گام، ممیزی فقط‌خواندنی است؛ نه اجرای ensureColumn، setup یا اصلاح خودکار ستون‌ها.

## 2. پیش‌شرط‌های هر مهاجرت

1. تأیید محیط و شناسایی شیت‌های دقیق هدف بدون افشای شناسه‌های محرمانه در log.
2. گرفتن نسخه پشتیبان قابل‌بازیابی از شیت‌های هدف و ثبت زمان/مسئول/دامنه پشتیبان.
3. استخراج header واقعی به ترتیب ستون‌ها و شمارش ردیف‌ها؛ ثبت نام ستون‌های مفقود، تکراری، اضافی و مقادیر غیرمنتظره به‌صورت گزارش، بدون تغییر داده.
4. بررسی کدهای خواندن/نوشتن که به نام header یا شماره ستون متکی‌اند و تعیین اثر هر اختلاف.
5. نوشتن migration کوچک، نسخه‌دار و قابل اجرای مجدد، همراه با تست fixture و معیار توقف.
6. بازبینی انسانی گزارش ممیزی و طرح بازگشت قبل از هر نوشتن.

اگر پشتیبان قابل‌بازیابی یا تشخیص محیط قطعی نیست، مهاجرت متوقف می‌شود.

## 3. سیاست تغییرات افزایشی

- ستون جدید، در صورت اثبات نیاز، فقط به انتهای header اضافه شود؛ ستون موجود حذف، جابه‌جا یا تغییرنام داده نشود.
- هیچ ردیفی برای «پاک‌سازی» خودکار حذف یا بازنویسی نشود.
- مقدار پیش‌فرض فقط وقتی اعمال شود که قرارداد کسب‌وکار آن را مشخص کرده باشد؛ از پرکردن دسته‌ای مقادیر وضعیت/واحد/کد قلم با حدس خودداری شود.
- داده legacy نامعتبر به صف گزارش/بازبینی منتقل شود؛ به‌جای اصلاح خاموش، شناسه ردیف و علت ثبت شود.
- migration دارای شناسه نسخه و اثر idempotent باشد؛ اجرای دوباره نباید ستون تکراری یا مقدار تکراری بسازد.
- عملیات تغییر داده دسته‌ای با اندازه batch محدود، شمارش قبل/بعد و کنترل خطا اجرا شود؛ هیچ تراکنش چندشیتی اتمیک فرض نشود.
- تغییر schema در DatabaseSetup.js تنها پس از تأیید اختلاف واقعی و تست سازگاری انجام شود.

## 4. ترتیب پیشنهادی اجرا

### مرحله A — ممیزی فقط‌خواندنی
برای هر شیت تأمین و محاسبات:
- نام شیت و وجود/عدم وجود؛
- header واقعی به ترتیب؛
- مقایسه با تعریف DatabaseSetup.js;
- ستون‌های تکراری/مفقود/اضافی؛
- تعداد ردیف‌ها و شمارش خالی بودن فیلدهای کلیدی (ID، TenantID و کلیدهای رابطه‌ای مربوطه)، بدون استخراج مقادیر حساس؛
- گزارش خروجی به‌صورت خلاصه قابل بررسی.

### مرحله B — تصمیم و طراحی
برای هر اختلاف، یکی از این نتایج ثبت شود:
- بدون اقدام: ستون اضافی legacy است و کد به آن وابسته نیست؛
- اصلاح کد: ساختار موجود معتبر است و فقط نگاشت کد نیاز به سازگاری دارد؛
- migration افزایشی: ستون واقعاً لازم است و نبود آن باعث خطای اثبات‌شده می‌شود؛
- توقف و بررسی انسانی: داده متناقض، header تکراری، ارتباط یتیم یا ابهام معنایی مشاهده شده است.

### مرحله C — اجرای محدود در محیط تست
- ابتدا روی کپی/پشتیبان تست؛
- اجرای migration نسخه‌دار و ثبت خلاصه تعداد تغییرات؛
- بررسی header و شمارش ردیف‌ها قبل/بعد؛
- اجرای آزمون‌های قرارداد، سرویس، tenant و idempotency؛
- اجرای دوباره migration برای اثبات idempotency؛
- تست مسیر خواندن/نوشتن برنامه روی داده تست.

### مرحله D — بازبینی و تصمیم بازگشت
بازگشت باید از پشتیبان تأییدشده یا migration جبرانی مشخص انجام شود. حذف ستون یا بازگردانی خودکار بر اساس حدس مجاز نیست. اگر برنامه بعد از migration خطا داد، نوشتن بیشتر متوقف و ابتدا اختلاف‌ها و گزارش عملیات بررسی شود.

## 5. معیار توقف فوری

- محیط یا شیت هدف مبهم است؛
- پشتیبان قابل‌بازیابی تأیید نشده؛
- header تکراری یا جابه‌جایی‌ای وجود دارد که نگاشت کد را نامطمئن می‌کند؛
- ردیف دارای TenantID/کلید رابطه‌ای خالی یا ارجاع یتیم پیدا می‌شود و معنای آن روشن نیست؛
- تعداد تغییرات واقعی با تعداد پیش‌بینی‌شده تفاوت دارد؛
- آزمون تکرار امن، دسترسی tenant یا قرارداد API شکست می‌خورد.

## 6. ماتریس بازگشت
